# Concurrent Reservation System

A backend API built with **FastAPI** and **PostgreSQL** that demonstrates two classic strategies for handling concurrent bookings:

- **Pessimistic Locking** (`SELECT ... FOR UPDATE`) – locks the room row to prevent conflicts.
- **Optimistic Locking** (version column) – uses a version number to detect and reject conflicting updates.

The system is fully tested with **pytest** and **Docker**, including 10 simultaneous requests for the same room.

## Getting Started

### Prerequisites

- Docker and Docker Compose installed

### 1. Clone the repository

```bash
git clone https://github.com/andreasoledadguerra/reservation_system.git
cd reservation_system
```

### 2. Start the services

```bash
docker compose up -d
```
This will build the API Image, start PostgreSQL, and launch the FastAPI server.


### Run the tests

```bash
docker compose exec api pytest tests/test_concurrency.py -v
```

You should see both tests pass:

- test_pessimistic_concurrency PASSED

- test_optimistic_concurrency PASSED


## API Endpoints

### Pessimistic booking

```http
POST /api/v1/bookings/pessimistic/{room_id}
Content-Type: application/json

{
    "email": "user@example.com"
}
```
- Returns 200 on success, 400 if no availability and 404 if room not found.

### Optimistic booking

```http
POST /api/v1/bookings/optimistic/{room_id}
Content-Type: application/json

{
    "email": "user@example.com"
}
```
- Returns 200 on success, 409 if a concurrency conflict is detected, 400 if no availability and 404 if room not found.


## How Concurrency Control Works

### Pessimistic Locking
Before updating the room, the transaction does a SELECT ... FOR UPDATE, which locks the row. Other concurrent requests must wait until the lock is released. Only one booking succeeds.

### Optimistic Locking
The rooms table has a version column. When updating, the query includes WHERE version = :current_version. If another request already changed the row, the version no longer matches and rowcount is 0. The conflict is returned as a 409 status, and the client should retry.


## Testing Concurrency
The test suite simulates 10 users booking the same room simultaneously:

test_pessimistic_concurrency: exactly 1 successful booking and 9 failures (no availability).

test_optimistic_concurrency: exactly 1 successful booking and 9 conflicts (409).

These tests guarantee that the concurrency mechanisms are working correctly.
